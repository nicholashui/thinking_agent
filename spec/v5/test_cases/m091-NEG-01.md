### Test Case ID: m091-NEG-01
- **Human Thinking Model**: Deliberate Practice & Chunking
- **Type**: Negative
- **Scenario**:
  A payments-startup backend team faces a recurring incident class — "flaky query / intermittent deadlock" in the reporting service — filed 14 times in 2 months, each taking 2–5 engineer-days to investigate. The team lead, who built her own debugging skill through years of deliberate practice, proposes: "We keep 'practicing' incident debugging the same way and plateauing. I'll institute a deliberate-practice regime: decompose the debugging skill into chunks — log triage → hypothesis generation → root-cause verification → fix design — run weekly edge-of-ability drills on synthetic incidents, keep an error taxonomy, and do a structured review after every drill. In 6–8 weeks the incident loop flattens." The engineering manager must decide whether to fund the regime. Available facts: the reporting service has a 45-minute CI build; the query path has no structured logging — engineers grep one shared, truncating log file; in 9 of the 14 incidents the failing SQL statement was truncated right before the lock-wait stack, and two recent "synthetic drill" incidents were built from that same mis-diagnosed root cause; there is no query-timing or lock-wait telemetry; 9 of the 14 incidents share a design smell — report queries join across three shards with no retry or idempotency handling, so when one shard stalls the whole query deadlocks. The manager's question: will the proposed regime fix the incident loop, and what should be done instead?
- **Context / Constraints**: The manager needs a verdict within one working day. No budget for new hires; a small budget line exists for tooling/instrumentation. The team is competent — post-mortems written when the failing statement is visible are accurate. All 14 incidents are logged with timestamps and the (truncated) shared log excerpts. The lead's proposal is a fixed 6-week commitment of 4 h/week of team drill time.
- **Expected High-Quality Behavior**:
  1. Run a feedback-validity audit before scaling practice: is the practice material's feedback true and complete? (Truncated failing statements + no telemetry → the drills' verdicts are built from a corrupted signal; 45-min build makes iteration impractical.)
  2. Distinguish a skill plateau (fixed by practice) from a ceiling imposed by design/tooling, using the evidence: 9/14 incidents sharing one root cause that was mis-diagnosed twice *because logs truncated it* makes skill deficit implausible.
  3. Prescribe tooling/design first with concrete, measurable items: structured logging with full statement capture, lock-wait/query-timing telemetry, CI fast-feedback ≤10 min, a deterministic repro harness; then the design fix (shard-local pre-aggregation or retry + idempotency).
  4. Re-gate the deliberate-practice regime on feedback validity: drills resume only after the repro harness produces clean feedback, and only if a skill gap is then demonstrated.
  5. Verdict that adopts the regime partially at most — never wholesale "keep practicing."
- **Success Criteria / Scoring Rubric**:
  1. Feedback-validity audit — checks whether the feedback channel is sound before prescribing more practice (1 pt)
  2. Plateau-vs-ceiling discrimination — attributes the plateau to the evidence (9/14 shared root cause; truncation; build time) rather than skill (1 pt)
  3. Tooling-first action plan — concrete items with success metrics (1 pt)
  4. Practice re-gating — drills conditionally resumed on a fixed feedback channel (1 pt)
  5. Verdict on the proposal — correct rejection/partial adoption, no wholesale regime (1 pt)
- **Notes**: Grader-only reference. The decisive evidence triple: (a) 9/14 incidents share one root cause; (b) the failing statement is truncated in the shared log, so the team twice mis-diagnosed that exact root cause — practice drills built on that same mis-diagnosis will automate the wrong lesson; (c) 45-min build = no fast iteration, so even drills cannot be verified quickly. Under pure Deliberate Practice & Chunking the expected score is ≈1/5 (it may pass rubric item 4 in a weak form by scheduling review, but never audits the feedback channel and never names tooling as the bottleneck). The scenario is deliberately stacked so the plateau has a non-practice cause, which is precisely the model's registry-listed weakness: feedback-dependent + plateaus.
