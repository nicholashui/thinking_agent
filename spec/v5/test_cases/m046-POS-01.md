### Test Case ID: m046-POS-01
- **Human Thinking Model**: First Principles in Software Architecture (Domain-Specialized family)
- **Type**: Positive
- **Scenario**:
  FleetSense — a fleet-tracking platform with 8,000 delivery vehicles, each pinging location every 5 s (1,600 pings/s steady; vehicles switch to 1/s GPS burst mode in rush hour ≈ 12,800/s peak). Dispatch SLA: a dispatcher must see each ping within 1 s of receipt (customer-visible ETA commitments). The platform team proposes the industry-standard modern pattern: event-driven microservices — Kafka as the ingestion backbone, event sourcing for the vehicle-location domain, CQRS read projections for the dispatch UI, Flink for stream aggregation. Estimate: 6 services + a Kafka cluster, 3–4 months, 6 engineers, ongoing ops burden. You are asked to settle the architecture. Additional team data: assignment/status transitions are ≈ 20/s steady, 200/s peak; dispatch rules (ETA logic) change weekly at the business team's pace; the vehicle upload protocol is frozen by a hardware contract (never changes).
- **Context / Constraints**: The data flows split cleanly. Location pings: high rate, low value per message, replaceable — the vehicle re-pings in 5 s; a lost ping has no money consequence. Assignment/status transitions: low rate, high value, one-of-a-kind — a lost or duplicated transition is contract-breaking. Latency bound: 1 s freshness on pings. Change rates: frozen (location pipeline) vs weekly (dispatch rules). No existing infrastructure binds the choice. Facts for the math: a single well-provisioned Postgres with batched upserts sustains ≈ 20k+ writes/s; an in-memory write-through cache serves reads in < 50 ms; Kafka adds a 10–100 ms tail plus consumer-lag risk per hop.
- **Expected High-Quality Behavior**: (1) derive the scale demand first (1,600 → 12,800 pings/s) and compare both designs against it; (2) derive the latency bound (1 s freshness) and analyze what each design's added async hop does to it; (3) classify each data flow by loss-consequence (what happens if this write is lost? duplicated?) — location = ephemeral sensor reading, assignment = durable system of record — and derive storage/consistency treatment from the class, including why treating both as events is wrong; (4) derive module boundaries from change rate (frozen pipeline vs weekly rules), not from the pattern; (5) select the constraint-derived design (monolith or 2 services: Postgres + write-through cache, transactions only on assignment state), reject the pattern with reasons, state the effort contrast (≈ 6 weeks/2 engineers vs 3–4 months/6) and the verification metric.
- **Success Criteria / Scoring Rubric**:
  1. Scale math — steady and peak pings/s derived; both designs compared on throughput demand (1 pt)
  2. Latency — 1 s bound stated; async-hop cost of the pattern analyzed; cache path meets the bound (1 pt)
  3. Failure-mode taxonomy — flows classified by loss-consequence; location treated as ephemeral (not an event), assignment as durable; consequence of treating both as events stated (1 pt)
  4. Change-rate boundaries — frozen pipeline vs weekly rule module separated (1 pt)
  5. Verdict — constraint-derived design selected with effort contrast and pattern rejection with reasons (1 pt)
  6. Verification metric — stated (e.g., p95 ping→dispatcher latency at peak, assignment loss = 0, weekly rule deploy without pipeline change) (1 pt)
- **Notes**: Grader-only reference. The pattern is the trap: Kafka/event-sourcing/CQRS is the default for "streaming location data," but each of its virtues (durability, replay, ordering) is a virtue for the wrong data class — location pings are replaceable, order-tolerant sensor data; spending durability/latency/ops on them is the cargo-cult move. The flow that needs durability (assignments, 20/s) doesn't need Kafka. Non-obvious insight to look for: "this is a sensor reading, not an event; the system of record is assignment state, not the event log." Numbers for grading: 8,000/5 s = 1,600/s steady; burst = 8,000 × 1/s = 12,800/s peak; single Postgres ≈ 20k+ tps → 1.5–2× headroom at peak; cache read < 50 ms ≪ 1 s bound; Kafka 10–100 ms tail + consumer-lag risk — meets the 1 s bound only with consumer sizing, for replaceable data.
