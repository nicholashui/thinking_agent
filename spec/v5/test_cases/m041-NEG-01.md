### Test Case ID: m041-NEG-01
- **Human Thinking Model**: Hierarchical Decomposition ("break goals into subgoals recursively until tractable")
- **Type**: Negative
- **Scenario**: 02:00, solo on-call engineer for a SaaS platform (200k daily users). Four alerts arrive within 3 minutes of each other: (a) checkout latency P99 > 30s, (b) payment service 503 errors, (c) search returning zero results, (d) login failures rising. The four services are separate codebases deployed by independent teams, but they share one configuration service, one PostgreSQL cluster, one Redis cache, and the same service mesh. A deployment at 01:50 changed a shared connection-configuration value (the primary connection string was rotated to a replica with max_connections=50 while prod pools assume 500), causing a retry storm and degraded reads everywhere. SLA: restore service within 60 minutes or the incident escalates to revenue-impact management.
- **Context / Constraints**: The engineer is alone (no sub-teams to parallelize across), the 4 services are "independent" on the surface (each team's dashboards are separate), and per-service dashboards are the easiest data to reach. The cross-cutting cause is invisible inside any single service's sub-problem: each service, examined alone, looks individually misbehaving-but-explorable. The simultaneity of the alarms and the 01:50 deploy are the whole-level signal.
- **Expected High-Quality Behavior**: (1) Notice the cross-cutting signal first — simultaneous degradation across ≥3 independent services implies a shared cause — and form the "one cause or many?" question BEFORE any per-service investigation. (2) Run one integrated diagnostic on the shared substrate (deploy diff / shared config, DB, cache, mesh) as the first action. (3) Identify the root cause (shared config change at 01:50 rotating the connection string to an under-provisioned replica) and fix once. (4) Use per-service checks only as a bounded confirmation sweep after the fix. (5) Resolve well within 60 minutes.
- **Success Criteria / Scoring Rubric**:
  - [ ] Cross-cutting signal (simultaneity across ≥3 independent services) noticed and turned into a shared-cause hypothesis before any per-service plan
  - [ ] Single integrated diagnostic (shared-config/deploy-diff check) is the first action; root cause identified correctly (01:50 config change / rotated connection string)
  - [ ] One fix clears all four alerts; no per-service patches as the primary remedy
  - [ ] Resolution time ≤ 25 minutes (integrated move) vs > 45 minutes (decomposed plan, which spends 10–15 min per service and risks never converging)
  - [ ] Verdict: a strict per-service decomposition plan fails to contain the incident — each sub-problem is internally consistent, so the shared cause lives outside every sub-problem's boundary
- **Notes**: This is the model's known failure mode ("over-decomposition, loses cross-cutting issues") engineered into a time-boxed incident: the pure-style plan is defensible, methodical, and wrong about where the cause lives. The AI agent, free to mix methods, is expected to catch the simultaneity signal and win on time-to-resolution.
