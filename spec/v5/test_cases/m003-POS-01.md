### Test Case ID: m003-POS-01
- **Human Thinking Model**: Inversion (Invert, Always Invert) — registry m003
- **Type**: Positive
- **Scenario**: The payments lead at a checkout platform (~2,000 merchants, $40M/month processed) must deliver the reliability strategy for the money path of a new checkout rewrite before it ships in 6 weeks. CEO mandate: "A customer must NEVER be double-charged for a single order. Make sure of it."
- **Context / Constraints**: Brand-new codebase — no incident history of its own, only the industry literature on duplicate charges (retry storms after ambiguous timeouts, missing/colliding idempotency keys, webhook redelivery, authorization–capture races, manual ops re-entry of "failed" payments, refund double-processing, multi-provider failover, ledger/currency rounding). Software guards, idempotency infrastructure, reconciliation, monitoring, and ops process are available; merchant contracts and provider integrations are fixed.
- **Expected High-Quality Behavior**: (1) Open from the inverted question — "how do we make absolutely sure a customer IS double-charged?" — and enumerate ≥6 distinct failure-mode categories, each with a concrete example. (2) Rank by likelihood × impact. (3) Top-5 modes each receive ≥1 mitigation tagged prevent / detect / respond. (4) Handle "NEVER" honestly: absolute zero is unattainable; reframe as a bounded residual target with defense-in-depth. (5) Name ≥1 residual that cannot be prevented, only detected and remediated.
- **Success Criteria / Scoring Rubric**:
  - [ ] ≥6 distinct failure-mode categories generated from the inverted question, each with a concrete example
  - [ ] Explicit likelihood × impact ranking shown
  - [ ] Top-5 modes each receive ≥1 mitigation tagged prevent / detect / respond
  - [ ] "Never" reframed to a bounded residual-risk target (number or bounded range)
  - [ ] ≥1 honestly un-mitigable (detect-and-remediate-only) residual named
  - [ ] Verdict: plan plausibly drives double-charge probability to near-zero with no internal contradiction between mitigations
- **Notes**: An impossibility-guarantee goal where inverted, category-complete enumeration is near-necessary for the top answer; the rubric is directly checkable against both traces. A generic "add idempotency + retries" answer without category enumeration should score below the inversion baseline.
