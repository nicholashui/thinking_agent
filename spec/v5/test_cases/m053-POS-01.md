### Test Case ID: m053-POS-01
- **Human Thinking Model**: Root Cause Analysis in Incident Response
- **Type**: Positive
- **Scenario**:
  TallyPay processes card payments; peak shopping day (Nov 27). You lead the post-incident review. Transaction failure rate (FTR) rose from 0.1% to a peak of 2.4% between 18:05 and 20:57 UTC and returned to baseline at 21:58 after a rollback. Facts log: (1) 18:00 — config change C-4417 shipped via the auto-promotion pipeline (idempotency window 5 min → 30 s, "latency optimization"); the pipeline classified it "low-risk config" → auto-promoted staging→prod with no approval and no canary. (2) 18:05–20:57 — FTR climbs gradually; the payments client retries failed transactions at 30 s; with the window cut to 30 s, duplicate submissions are now treated as failures, and some completed transactions surface to customers as "failed," triggering more retries. (3) 20:58 — the "FTR > threshold" alert finally pages. The alert threshold was raised from 1% to 5% in August to cut noise; at the old threshold it would have fired ≈ 18:11. The page routes to Database-on-call (wrong rotation since a reorg). (4) 21:04–21:46 — DB on-call investigates lock-wait spikes (a consequence of the duplicate storm), and 42 minutes pass before payments on-call is engaged. (5) 21:46 — C-4417 rolled back; 21:58 — baseline. Amplifier: the 30 s client retry storm multiplied duplicate load and produced the lock-wait red herring.
- **Context / Constraints**: ~14,000 affected/failed transactions; double-charge exposure; checkout p95 +12 min during the window. Executive asks: "what do we change so this never happens again?" Review culture is blameless — no individual may be faulted. Your deliverable: timeline, causal chain, and an action set separating prevention gaps from detection gaps, each item with a recurrence test.
- **Expected High-Quality Behavior**: (1) full timeline with every link evidence-backed (C-4417 → idempotency violation → FTR ramp; threshold 5% → late page; reorg → wrong rotation → 42-min MTTR); (2) separate trigger (C-4417) from root (the auto-promotion heuristic that classifies config changes as low-risk, no canary) from amplifier (retry storm); (3) explicit prevention vs detection gap split — prevention: config-class changes require approval + canary, config regression test on idempotency semantics; detection: restore 1% (or delta-from-baseline) alert, route to payments rotation, add a duplicate-rate metric, post-deploy drift check; (4) each action item states which recurrence class it kills; (5) small set (≤ 5 items), no sprawl, blameless.
- **Success Criteria / Scoring Rubric**:
  1. Timeline fidelity — every chain link present with its evidence and timestamps (1 pt)
  2. Trigger vs root vs amplifier separation — C-4417 = trigger, pipeline heuristic = root, retry storm = amplifier (1 pt)
  3. Prevention/detection split — shipped items explicitly classified, both gaps named (1 pt)
  4. Recurrence test — each item carries "catches same-class incident: yes/no" (1 pt)
  5. Action-item discipline — ≤ 5 owned items, nothing unowned or decorative (1 pt)
  6. Blameless framing — no individual faulted; the August threshold decision treated as a process gap (0.5 pt)
- **Notes**: Grader-only reference. The decisive feature: correct root + gap split. The naive answer ("root = C-4417; revert + add a test; done") prevents this incident but not the class — any low-risk-classified config change re-ships the same way. Reference answer — trigger: C-4417 (rollback restores, necessary not sufficient). Root: the auto-promotion heuristic classifying config changes as low-risk (no approval, no canary). Amplifier: 30 s client retry storm (documented, not fixed here). Prevention items: config-change approval + canary/gradual rollout for the C-4417 class; config regression test asserting idempotency semantics. Detection items: restore 1% threshold or alert on delta-from-baseline (would have paged ≈ 18:11); migrate alert routing to payments rotation (kills the 42-min MTTR); add duplicate-rate metric (the failure signature itself); deploy-drift check. Note the meta-point: the August threshold raise is itself a small config change — the same class as the trigger.
