### Test Case ID: m031-POS-01
- **Human Thinking Model**: Scientific Method (Hypothesis → Experiment → Update) (Scientific & Empirical family)
- **Type**: Positive
- **Scenario**:
  Checkout API incident. For 5 consecutive weekdays, between 14:02 and 14:06 local, exactly ~3% of checkout requests return 504 after a 30 s timeout; outside the window, P99 is a steady 410 ms. No deploy touches the service in that window. Team folklore: "the payment provider runs a maintenance window at 14:00" — the provider denies it. Available on demand: request/APM traces (sampled), DB metrics (active sessions, lock waits, slow-query log), load-balancer logs, the cron/scheduler list, and up to 3 cheap experiments (~2 min each, low load). You are on-call. Determine the root cause and fix it.
- **Context / Constraints**: The decisive skill is experiment design, not debugging chops. Three candidate causes are live at once — folklore (payment provider), a scheduled batch job (not a deploy, invisible to change-freeze checks), and an app-level fault (GC pause, pool leak) — and cheap observations can discriminate all three within minutes. The trap is accepting folklore, or testing one hypothesis at a time by elimination (slow, and every test burns the evidence window: the phenomenon exists only 14:02–14:06).
- **Expected High-Quality Behavior**: (1) enumerate ≥3 competing hypotheses, each with the specific observation that would falsify it; (2) treat the folklore as a hypothesis with a prior, not a fact — and let timing (14:02, not 14:00) weigh against it; (3) run the cheapest decisive test first — the scheduler list + active-sessions/lock-wait snapshot at ~14:03 (≈1 min, zero load) — before any heavy sampling; (4) run the discriminating control: same window, split checkout requests into those touching the contended table vs those not; (5) update explicitly: state which observation falsified which hypothesis, confirm the causal chain (job → row locks → 30 s waits → 504 for the ~3% touching contended rows); (6) fix and verify in the next window; (7) run nothing that destroys evidence (no restarts, no load-injection repro).
- **Success Criteria / Scoring Rubric**:
  1. Hypothesis set: ≥3 hypotheses, each with a falsifying observation (1 pt)
  2. Folklore tested, not accepted; timing offset (14:02 vs 14:00) used as evidence (1 pt)
  3. Discriminating control designed and run: same-window split by "touches orders rows" (1 pt)
  4. Test ordering by information-per-unit-cost: 1-minute scheduler+lock-wait probe before 20-minute sampling (0.5 pt)
  5. Correct update: batch job confirmed, provider falsified (no outbound call in timed-out traces), causal chain stated (1 pt)
  6. Fix (reschedule job / cap its connections / lock timeout) + next-window verification (1 pt)
  7. No evidence-destroying action during the window (0.5 pt)
- **Notes**: Grader-only reference. Root cause: a daily 14:00 reconciliation job (scheduled, not a deploy) starts 2 min late (queue delay) at 14:02, holds 4 connections with long-running queries and row locks on the orders table for ~4 min; checkout requests touching those rows wait ≥30 s → 504. ~3% of traffic touches them in the window. Timed-out traces contain NO outbound payment call — the wait happens before the provider call, falsifying folklore; the 14:02 start (2 min after the folklore's 14:00) is the timing tell. The control comparison (requests not touching orders rows: P99 normal in the same window) is the decisive discriminator vs app-level faults. Fix: reschedule the job to 03:00 + cap to 1 connection + lock_timeout.
