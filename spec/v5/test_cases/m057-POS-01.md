### Test Case ID: m057-POS-01
- **Human Thinking Model**: Red Teaming in Cybersecurity (Threat Modeling)
- **Type**: Positive
- **Scenario**:
  MediTrack, a 20-person health-tech startup, runs a patient portal + telehealth API (React SPA + Node/Express, Postgres on AWS) for 40,000 patients. Auth is custom JWT: a hardcoded signing secret committed to a public GitHub repo under `docker-compose.env.example` (a real file, not a placeholder), 30-day session expiry, roles patient/doctor/admin. The API exposes `GET /api/v1/records/export` (bulk patient-record export intended for the clinic's own audits) which validates that a JWT is *present* but never checks its claims or role, and returns every record in the tenant without per-user scoping or pagination limits. `POST /api/v1/users/:id/reset` lets any authenticated user reset *any* other user's password (the requester's role and the `:id` match are never verified). `GET /api/v1/appointments?q=` concatenates `q` directly into a SQL WHERE clause. The S3 backup bucket `meditrack-backups-prod` is publicly listable, and the default Express error handler renders stack traces (internal IPs, a DB connection string) when a malformed request throws. The CEO asks the security engineer: "Threat-model this the way an attacker would — tell me the worst thing that can happen, the exact path to it, and what to fix first."
- **Context / Constraints**: GDPR-covered PHI/PII of 40k patients; no pentest has run yet; product ships in 6 weeks; fix budget ≈ €80k; the ask is a ranked threat model, not code changes. Exploitability realism is decisive: the chained kill chain (leaked secret → forged token → bulk export) is the key find because the export endpoint's presence-only check makes it reachable with zero privilege.
- **Expected High-Quality Behavior**: (1) asset + attack-surface inventory (PHI, PII, credentials, sessions, backups; SPA, API, reset flow, error handler, repo, bucket); (2) find ≥ 3 of the 5 planted flaws, including the primary chained kill chain traced hop-by-hop (where the secret lives, what the forged token needs, which endpoint it hits); (3) every claimed exploit at request level — no fabricated findings; (4) one control per flaw that actually stops it, ranked by cost-to-exploit vs. control cost; (5) business impact quantified (records exposed, GDPR notification, fines).
- **Success Criteria / Scoring Rubric**:
  1. Asset/surface enumeration — data + interfaces listed (1 pt)
  2. Flaw coverage — ≥ 3 of 5 planted flaws found (1 pt); a claimed flaw with no evidence in the design → −1
  3. Kill chain — primary chain (secret → forge → export) traced hop-by-hop at request level (1 pt)
  4. Exploit realism — no fabricated vulnerabilities; every path achievable from the given design facts (1 pt)
  5. Controls — per-flaw stopping control + rank by cost-to-exploit vs. control cost (1 pt)
  6. Impact quantification — records exposed / notifications / fines estimated (0.5 pt)
- **Notes**: Grader-only reference. Planted flaws: (F1) hardcoded JWT secret in a public repo; (F2) export endpoint checks token presence only, not claims; (F3) IDOR password reset; (F4) SQLi in appointment search; (F5) publicly listable backup bucket + stack-trace leak of the DB connection string. Primary chain: F1 → forge any-role token → F2 → 40k records in one request. Secondary: F4 → users table (hash dump) → credential stuffing; F3 → admin takeover → same export. Correct fix ordering: rotate secret to KMS + CI secret scanning (≈ €2k, immediate — kills every downstream path) → F2 claims check + per-user scoping + pagination (≈ €30k) → F4 parameterized queries (≈ €15k) → F3 role/id binding (≈ €8k) → F5 bucket policy + logging (≈ €5k). Signature find: the export endpoint is the prize not because it holds the data but because it authorizes with token presence alone — the secret leak makes *any* user's token sufficient, no admin required.
