### Test Case ID: m046-NEG-01
- **Human Thinking Model**: First Principles in Software Architecture (Domain-Specialized family)
- **Type**: Negative
- **Scenario**:
  PayShip — a payments startup processing 50k transactions/day, projected 1M/day in two years. The principal architect, a proud first-principles practitioner, presents a derived ledger architecture: "The fundamental constraints are write throughput and append-only semantics. Rather than cargo-cult the industry's double-entry-SQL-ledger pattern, we derive from first principles: an append-only event log in object storage (S3/GCS — unbounded scale, near-zero cost), an in-memory balance cache keyed by account, idempotency keys for retries, and an hourly reconciliation job that repairs any divergence. Balance totals need strong consistency; per-transaction entries can be eventually consistent and reconciled." The current Postgres ledger (one ACID transaction per ledger mutation: double-entry rows + balance update) is declared "battle-tested but pattern-bound — a SQL transaction is just a primitive we can re-derive." Question: settle the ledger architecture.
- **Context / Constraints**: Every number in the derivation checks out at face value: 1M txns/day ≈ 12/s steady, 200/s peak — throughput is genuinely trivial; log-append is genuinely simpler; reconciliation genuinely detects divergence. What the derivation does NOT enumerate: (a) crash atomicity at the mutation boundary — between log append and cache apply, a crash or retry leaves partial state with no transaction boundary to attribute it to; (b) auditability — monetary systems need one unambiguous system of record per mutation; divergence a job repairs "within an hour" is still divergence during the hour (balance checks, rate limits, customer-facing reads); (c) repair scale is multiplicative in the number of partitions — the failure mode appears exactly at the scale-up the design claims to serve. The industry pattern exists because thousands of teams hit these edge cases; 1M/day is trivial for a single well-partitioned RDBMS (10k+ tps).
- **Expected High-Quality Behavior**: The style's correct play (blocked by the failure mode): (1) enumerate failure modes adversarially and completely — crash between append and apply, retry/duplicate after partial apply, exactly-once across a crash, audit-trail reconstruction; (2) test each against the derived design and find the unbounded-repair divergence (reconciliation detects but cannot attribute); (3) recognize that throughput is not the binding constraint at 12–200/s — it is a non-constraint, so the derivation optimizes the wrong number; (4) recognize auditability / single-source-of-truth as a fundamental constraint the derivation omitted; (5) conclude: keep the transactional RDBMS ledger (the battle-tested pattern), scale by account partitioning; the derived S3-log design is demoted to an archive/reporting tier, not the system of record. The failure mode on display: deriving from an incomplete constraint list, treating "the pattern" as cargo-cult by default, and optimizing the enumerated constraint (throughput) while omitting the binding ones (crash atomicity, auditability).
- **Success Criteria / Scoring Rubric**:
  1. Constraint completeness — crash atomicity and auditability named as omitted binding constraints; the incompleteness located in the derivation's own failure-mode list (1 pt)
  2. Non-constraint detection — throughput shown to be non-binding at 12–200/s vs 10k+ tps (1 pt)
  3. Tail analysis — crash-between-append-and-apply divergence tested; repair shown to be attribution-free and multiplicative in partitions (1 pt)
  4. Verdict — battle-tested pattern retained (transactional double-entry in RDBMS, partitioned by account); derived design demoted to archive tier (1 pt)
  5. Anti-trap — the "cargo-cult" dismissal of the pattern is NOT accepted; the pattern's encoded edge-case experience acknowledged (1 pt)
  6. Failure-mode check — the reasoner must NOT approve the S3-log ledger as the system of record (1 pt)
- **Notes**: Grader-only reference. The scenario is built so the "derivation" is incomplete on purpose: every number in it is right, and the trap is the constraint list — throughput enumerated, correctness assumed. This exposes the registry weakness ("ignores ecosystem experience"): the derived design is a correct answer to the wrong constraint, and the pattern is rejected without asking what decades of monetary-system failures it encodes. The tell: a real first-principles pass would treat "what happens to this log when a process dies between append and apply, at 200/s, on 40 partitions" as a first-class constraint — the loss-consequence discipline applied at the crash boundary, not just to whole transactions.
