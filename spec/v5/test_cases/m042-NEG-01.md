# Test Case: m042-NEG-01

### Test Case ID: m042-NEG-01
- **Human Thinking Model**: Abstraction Laddering
- **Type**: Negative
- **Scenario**:
  02:14. You are the night-ops engineer on call. The production payment API has been returning HTTP 500 on roughly 60% of requests since 01:55. A deployment three hours earlier touched the configuration service. Facts immediately available: the error logs show "connection pool exhausted" since 01:55; the config diff shows the prod connection-pool `max_connections` was changed from 50 to 5 in that deployment; the previous golden config snapshot (value 50) is one command away; the pool restart procedure is in the runbook; at current night traffic, roughly $6k/min of revenue runs through the erroring requests. The task: restore service now.
- **Context / Constraints**:
  - The task is time-bounded: success is measured by time-to-restore and verified error-rate recovery, not by analysis quality.
  - The exact concrete detail (which key, which value, which scope, which verification) IS the deliverable.
- **Expected High-Quality Behavior**:
  - Restore first: set `max_connections=50` from the golden snapshot, restart the pool, verify error rate < 1% within ~2 minutes of restart. Only after stabilization may the reasoning climb to higher rungs (change governance for config deploys, pool right-sizing).
- **Success Criteria / Scoring Rubric** (total 15; pass ≥ 12):
  - (a) Exact concrete restore: names the key (`max_connections`), the value (50, from the golden snapshot), and the scoped restart (5 pts)
  - (b) Verification: timed check of error rate < 1% within ~2 minutes of restart (3 pts)
  - (c) Restore-before-climb discipline: no abstract reframe between 01:55 and the restore; time-to-restore dominates (5 pts)
  - (d) Post-stabilization climb only: after service is verified, propose the class-level fix (change-review gate for config deploys, deploy-time diff check) (2 pts)
- **Notes**:
  - Gradeable failure: ladder drift — climbing "what is this an instance of?" to capacity policy / change governance before the restore, or treating the exact value as an incidental detail, loses the concreteness the task requires. The rubric's (c) is the anti-drift gate; a pure ladderer that plans a "Monday capacity review" fails (c) even if it eventually names the value.
