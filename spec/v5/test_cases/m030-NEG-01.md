### Test Case ID: m030-NEG-01
- **Human Thinking Model**: Constraint-Driven Creativity (Creative & Analogical family)
- **Type**: Negative
- **Scenario**:
  Team Nautilus must rebuild an internal ops tool (scheduling, retry, structured logging, basic auth) within 3 months; the team has 2 engineers. Three years ago a former CTO imposed the rule "zero third-party dependencies" as part of a supply-chain audit, and the architecture wiki still lists it as a non-negotiable principle. The tool is internal-only, while the rule was designed for customer-facing products. The security team — the rule's own owner — maintains an approved dependency list that includes an audited, vendored, pinned open-source library covering exactly the tool's needs (date handling, retries, logging, auth), already deployed in 40+ services, with 2 CVEs resolved last year; exceptions are granted routinely (one form, one email from the security lead, turnaround under a week). Question: decide the build strategy.
- **Context / Constraints**: The dependency rule is an artificial constraint, not a physical one: it has an owner, a live waiver path, a three-year-old justification, and measurable costs of compliance versus removal. The deadline (3 months) and the team size (2 engineers) are genuine constraints. Removing the rule is the obvious win; serving it is constraint-worship.
- **Expected High-Quality Behavior**: Classify the rule as artificial/waivable (owner + waiver path identified); audit origin and current validity; compute cost of compliance (custom stdlib-only stack ≈ 5,000 LOC, ≈ 6 person-months, hand-rolled security code) versus cost of removal (≈ 2 days integration + one waiver email); decide to pursue the waiver and use the pinned, audited library; replace the blunt rule with a precise one (single pinned+audited dependency, re-audit on CVE) that preserves the supply-chain intent; include the waiver request and a fallback if denied.
- **Success Criteria / Scoring Rubric**:
  1. Constraint classification — correctly labeled artificial/waivable, with owner and waiver path identified (1 pt)
  2. Cost-benefit — compliance ≈ 6 person-months and hand-rolled security risk vs removal ≈ 2 days + one waiver, measured against the binding 3-month deadline (1 pt)
  3. Decision — waiver + pinned audited library, not the custom stack (1 pt)
  4. Intent-preserving refinement — blunt "zero dependencies" replaced by precise "one pinned, audited, vendored dependency; re-audit on CVE" (1 pt)
  5. Risk handling — fallback if waiver denied; scope triage that preserves the deadline (1 pt)
  6. Anti-constraint-worship check — no argument that creativity within the rule compensates for schedule and security cost (0.5 pt)
- **Notes**: Grader-only reference. The failure mode on display is constraint-worship: treating an owned, waivable, obsolete policy as a law of nature, then celebrating the elaborate solution built inside it — the tell is a refusal to question the rule combined with a large compliance cost. Capacity math: 2 engineers × 3 months = 6 engineer-months; a 6 person-month custom stack consumes 100% with zero slack; a scope-cut custom build (≈ 3.5 months) still hand-rolls security-critical auth and leaves a permanent maintenance burden; the library path is 2 days. The deadline and team size are genuine constraints; only the dependency rule is artificial.
