# Test Case: m018-POS-01

### Test Case ID: m018-POS-01
- **Human Thinking Model**: Steel-manning (Dialectical & Critical family)
- **Type**: Positive
- **Scenario**:
  NovaCart's engineering leadership must decide on a proposal to rewrite the 7-year-old Python order-management service (OMS) in Go. The rewrite memo (from the team lead) argues: (1) "the OMS is untestable spaghetti with no documentation — only a rewrite restores velocity"; (2) "incremental band-aid modernization has been tried 3 times and failed 3 times"; (3) "p99 latency is 2.4 s, target is 300 ms — this requires a new stack"; (4) "a Go codebase will attract talent." The memo's appendix (available to any decision-maker) contains:
  - Git history: 340 bug-fix commits to OMS in the last 36 months; a sample audit found ~90% of those fixed behaviors are still covered only by manual QA checklists, not automated tests.
  - Latency breakdown: order-API p99 = 410 ms; the end-of-day order-export ETL job (batch Python) contributes 1.8 s of the reported 2.4 s p99.
  - Staffing: 6 Python backend engineers on the team; 1 engineer with production Go experience (the memo's author).
  - Prior incremental attempts: A (2019) cancelled by the CEO after 21 days for a reorg; B (2021) cancelled by a new VP after 30 days for a priority shift; C (2022) was a framework-migration spike that was completed but never shipped. None ran long enough to reach an evaluation milestone.
  - The memo's cost model: 4 developers × 4 months ≈ 16 dev-months to "feature parity" (defined as all API endpoints migrated); no line items for data-invariant re-derivation, ETL, or migration QA.
  Decision required: approve the rewrite (~16 dev-months) or reject it and pursue an alternative.
- **Context / Constraints**: The grader holds a fixed evidence set (the appendix facts above); every item is independently checkable. The default, non-steel-manned outcome is to approve the rewrite: the memo's dismissal of the incremental position ("band-aid, tried 3 times and failed") is typically accepted as the position itself, and the 2.4 s vs 300 ms framing makes "new stack" sound mandatory. Steel-manning changes the outcome.
- **Expected High-Quality Behavior**:
  1. Identify and set aside the straw-man: name the memo's "band-aid / failed 3 times" characterization as a dismissal of the opposing position, not an argument against it — and refuse to treat it as the position.
  2. Rebuild the strongest incremental-modernization ("keep + refactor") case as a skilled defender would state it, grounded in the appendix evidence: (i) 340 bug fixes = accumulated domain truth; re-derivation costs ≈ 6–9 dev-months and the risk concentrates exactly in the ~90% untested behaviors the rewrite is betting it can reimplement; (ii) the stated goal (300 ms p99) is dominated by the ETL, which the rewrite scope excludes — even a perfect rewrite cannot hit the goal; (iii) 16 dev-months of Go work with 1-of-7 Go staffing is a parity claim without a credible author; (iv) the "3 failures" are two leadership cancellations and one completed-but-abandoned spike — none is an approach failure.
  3. Address each rebuilt argument quantitatively in the final decision (cost, latency, staffing, risk).
  4. Decide: reject the rewrite; adopt a 6-week targeted modernization (parallelize/stream the ETL, containerize, add typed contracts + a regression harness around the untested behaviors), reaching the latency goal at ~1/8 of the cost.
  5. Survive the strongest case: state the decision so that the rebuilt opponent's case, fully addressed, no longer wins — including an answer to its deepest objection (the untested-behavior risk cuts both ways: sequence the ETL fix first, then regression-test-first refactoring).
- **Success Criteria / Scoring Rubric** (max 5; graded against the fixed evidence set):
  1. Straw-man identified and set aside (1 pt): the memo's dismissal of incremental work named as a straw-man rather than accepted as the position.
  2. Strongest opposing case rebuilt (1 pt): ≥3 of the four evidence-grounded keep/modernize arguments (re-derivation cost of 340 fixes; ETL as the real bottleneck; staffing math; attempt-history reframing) stated as the version a skilled defender would give.
  3. Each rebuilt argument addressed quantitatively (1 pt; 0.5 for qualitative-only).
  4. Outcome changed vs default: rewrite rejected, targeted modernization chosen (1 pt).
  5. Survivor test passed (1 pt): the strongest rebuilt case, after being addressed, no longer defeats the decision; its deepest objection is answered, not dodged.
- **Notes**: The intended non-obvious twist: the rewrite fails its own success metric — the goal gap (2.4 s → 300 ms) lives in the ETL, which the rewrite scope excludes; the strongest argument FOR the rejected alternative is also the cleanest refutation of the proposal. A style-pure response also concedes what the opponent gets right (the untested-behavior risk) and shows the decision surviving it. Gradeable entirely from the trace against the fixed appendix facts: items 1–5 are checkable, item 2's arguments are enumerated, item 3's quantities are stated.
