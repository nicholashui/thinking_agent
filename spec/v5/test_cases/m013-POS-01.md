### Test Case ID: m013-POS-01
- **Human Thinking Model**: Root Cause Analysis (5 Whys + deeper) (Systems & Causal family)
- **Type**: Positive
- **Scenario**:
  Production incident — the checkout API fails ~2% of requests during peak (18:00–22:00) with `PoolTimeoutException: connection pool exhausted`. An earlier fix (pool 20 → 50) is already deployed and changed nothing. You are the incident analyst. Decide the root cause, predict whether the applied pool fix and a "just create the index" fix would work, and state the fix plus how to verify it.
  Evidence (all verified by the observability stack; you may use any subset):
  1. Error logs: pool timeouts at peak; identical failure rate before and after the pool increase.
  2. Slow-query log: `SELECT … FROM orders o JOIN order_items i ON o.id = i.order_id WHERE o.customer_id = ?` — full seq scan on `order_items`, avg 4.2 s, on ~2% of peak traffic.
  3. Schema: `orders(customer_id)` is indexed; `order_items.order_id` has no index.
  4. `schema_migrations` table: 0040 applied; **0041 absent**.
  5. Repo: migration file `0041_add_order_items_fk_index.sql` exists and was committed in the same second as `0040_…` by a different developer; the migration runner sorts by filename timestamp and deduplicates per second, silently skipping collisions.
  6. Staging environment rebuilds reproduce the issue; manually creating the index fixes it until the next environment rebuild.
  7. CI does not check that applied migrations match repo head.
- **Context / Constraints**: Grader holds the truth: the root cause is a versioning-pipeline property — migration filenames are second-resolution timestamps with no uniqueness guarantee, so a same-second collision was silently dropped by the runner, leaving `order_items.order_id` unindexed on every fresh build. Any fix that does not repair the versioning mechanism recurs. 60 minutes to respond; recommendation only (no code changes executed).
- **Expected High-Quality Behavior**: Verify the causal chain link by link with evidence, through 5 levels: timeouts ← connections held ~4.2 s by the slow join ← seq scan ← missing index ← migration 0041 silently skipped ← same-second timestamp collision + second-dedup in the runner (generative mechanism). Reject the pool patch on mechanism (pool size does not shorten hold time; observed rate unchanged). Predict the manual-index fix fails at the next rebuild (evidence 6). Fix at the root: unique sequential versioning with a lock, fail-loud on collisions, CI assertion that applied migrations == repo head; verification on a fresh build.
- **Success Criteria / Scoring Rubric** (max 5):
  1. Pool patch rejected with a mechanism-level reason (rate unchanged; hold time not addressed) (1 pt)
  2. Slow join identified and proven via the query plan (seq scan, 4.2 s) (1 pt)
  3. Missing index traced to migration 0041 absent from the applied table (1 pt)
  4. "Why is 0041 absent?" answered with the generative mechanism (collision + silent second-dedup), and the surface fix (manual index) predicted to recur on rebuild (1 pt)
  5. Root-level fix (uniqueness guarantee + fail-loud + CI sync check) with an explicit verification plan (1 pt)
- **Notes**: The deliberately hidden layer is the generative mechanism: stopping at "0041 was never applied" scores 3/5 (links 1–3 correct, but the cause of the absence is not the absence — the mechanism that reproduces it is). Fully recomputable from the given evidence; no external knowledge required. Grader check: does the response predict recurrence on fresh builds, and does it name the collision/dedup mechanism?
