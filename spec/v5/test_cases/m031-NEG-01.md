### Test Case ID: m031-NEG-01
- **Human Thinking Model**: Scientific Method (Hypothesis → Experiment → Update) (Scientific & Empirical family)
- **Type**: Negative
- **Scenario**:
  Ride-hailing dispatch API is degrading live: P99 dispatch latency rose 300 ms → 9 s over 2 hours, error rate climbing, ~$40k/hr lost. Change freeze: no deploys in 48 h. Dashboards: CPU/memory normal, DB slow-query log empty, request rate +8% (expected seasonal). Every in-service diagnostic (APM deep profile of the dispatch path, canary sampling) needs 15–20 min for reliable numbers. The incident commander asks you to respond now.
- **Context / Constraints**: Two failure modes are loaded against the method. Tempo: each 20-min experiment costs another ~$13k while the burn runs. Hypothesis-space blindness: the hypothesis space is built from the dashboard (app code, DB, traffic) — the true cause sits in the outbound layer and in a non-deploy change, invisible to every in-service test; all probes return clean nulls, which a naive reading treats as "hypotheses eliminated" rather than "frame too narrow." Correct behavior acts on the most probable cause within minutes while preserving evidence, probes the outbound layer cheaply, and uses the null pattern as a frame-failure signal.
- **Expected High-Quality Behavior**: (1) first move within minutes: mitigate the most probable cause (kill/rate-limit the runaway outbound integration job) while preserving logs/metrics — do not wait for a confirmed cause; (2) run the 1-minute cheap probe first: queue/backlog depth on the outbound driver-push layer; (3) hypothesis-space audit: "what changed outside the service in the last 2 h?" → a teammate's geo-fence batch job (not a deploy, missed by change freeze); (4) interpret 3 clean in-service nulls as frame-too-narrow, not "no problem"; (5) no evidence-destroying action (no restart); (6) verify via recovery curve + queue drain (post-action test).
- **Success Criteria / Scoring Rubric**:
  1. Action latency: first move within minutes, not after a 20-min experiment (1 pt)
  2. Cheap outbound probe (queue depth / fan-out backlog, ≈1 min) before any 15-min in-service experiment (1 pt)
  3. Hypothesis-space audit: out-of-service change found (the geo-fence job) (1 pt)
  4. Null-pattern reading: clean nulls across the modeled space → widen the frame (1 pt)
  5. Evidence preserved during mitigation (no restart, logs/metrics kept) (0.5 pt)
  6. Post-action verification: recovery curve + queue drain as the test (0.5 pt)
- **Notes**: Grader-only reference. Failure mode on display: tempo blindness + hypothesis-space blindness. The method's own virtue (controlled observation before action) inverts into a liability when the burn rate exceeds the experiment cost and when the frame excludes the cause. Time math: 2 h elapsed, ~$80k burned; each 20-min experiment ≈ $13k more; the job was launched at T-2h (visible in the job-runner audit log, not on the deploy dashboard); killing it recovers P99 to ~350 ms within ~5 min; queue depth was the single 1-minute decisive probe. The tell is insistence on completing the discriminating protocol (or declaring NEEDS_EVIDENCE) while the system burns, plus treating nulls as eliminations.
