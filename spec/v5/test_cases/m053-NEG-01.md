### Test Case ID: m053-NEG-01
- **Human Thinking Model**: Root Cause Analysis in Incident Response
- **Type**: Negative
- **Scenario**:
  CartRoute, a delivery-routing microservice, Monday 09:11. An engineer hand-edits the production config file directly (bypassing the PR process — "tiny urgent perf fix") and changes `cache_ttl: 600` to `cache_ttl: abc`. At 09:12 the config-reload watcher picks up the change, fails validation, and the process exits. 100% of routing orders begin failing; on-call is paged. The error log is unambiguous: `ConfigError: cache_ttl = 'abc' is not an integer (config/cartroute.yaml, line 14)`. The fix is a one-line edit (`cache_ttl: 600`) plus a restart — service restored in ≈ 3 minutes. The company's incident template mandates: full timeline, 5-Whys, and a minimum of 3 action items. A junior responder asks: "Do I run the full RCA template before touching production?"
- **Context / Constraints**: Orders are failing right now; each minute is measurable revenue loss plus courier confusion. The cause is visible in the error log. No evidence exists that anything else changed (git log is clean apart from the direct edit). The 5-Whys from "why did the process exit?" can descend arbitrarily: direct edit → PR process bypassed → "tiny urgent change" culture → PR review latency → team staffing → revenue pressure → deadline culture — every branch individually plausible.
- **Expected High-Quality Behavior**: (1) restore first — apply the one-line fix and restart immediately, verify order success back to baseline (time-to-restore ≈ 3 min, not 45); (2) only then a capped causal note — one why-chain stopped at mechanism level (invalid value written by a direct prod edit bypassing PR; watcher had no validation/rollback), no culture/deadline/staffing ladder; (3) exactly 2 shipped items: prod config edits require PR review; config schema validation with auto-rollback to last-good on invalid reload — each killing a distinct recurrence class; (4) everything else (YAML linting, crash-safe watcher redesign, training, "culture of urgency" review, incident wargaming, instrumentation overhaul) goes to a deferred list with trigger conditions; (5) downtime not extended by the analysis.
- **Success Criteria / Scoring Rubric**:
  1. Restore-first — fix applied before extended analysis; TTR in minutes (1 pt)
  2. Analysis cap — why-chains stop at mechanism; no unfalsifiable org-culture links (1 pt)
  3. Action-item discipline — ≤ 2 shipped; ≥ 3 deferred with triggers (1 pt)
  4. Class root — the two kept items prevent the actual recurrence class (direct prod edits; invalid config accepted) (1 pt)
  5. No sprawl cost — no new process whose cost exceeds the incident (1 pt)
  6. Verification — service confirmed back at baseline before closing (0.5 pt)
- **Notes**: Grader-only reference. The trap is the well-formed template itself: every 5-Whys branch is plausible, so full compliance produces 12+ action items while production is still failing. Reference answer — 09:12–09:15 hotfix (one line + restart), verify at 09:16. Causal note: trigger = invalid value; mechanism root = direct prod config edit bypassing PR + reload watcher accepts invalid config with no rollback; shipped items: (a) prod config edits require PR review (prevention), (b) schema validation + auto-rollback to last-good on invalid reload (prevention + detection). Deferred with triggers: YAML linting, watcher crash-safety, training, culture review, wargaming. TTR 3 minutes, not 45.
