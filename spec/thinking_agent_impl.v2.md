When an implementation detail is not explicitly defined by the source specification, this document provides the required engineering elaboration. Such elaborations must preserve the source specification’s invariants, terminal-state contract, governance boundaries, and validation requirements.

- **MUST**: mandatory for conformance.
- **MUST NOT**: prohibited.
- **SHOULD**: expected unless a documented engineering reason justifies an exception.

Repository acceptance tests SHOULD reject accidental introduction of `Dockerfile`, `docker-compose.yml`, `compose.yaml`, or equivalent deployment artifacts.

# 1. Executive Summary

## 1.1 Objective

Implement Thinking Agent v8 as a governed, stateful, auditable problem-solving system whose core task loop is:

```text
META-CONTROL
    → WHAT
    → WHY
    → HOW
    → DO
    → REVIEW
```

A continuous verification layer surrounds all stages. A governance and safety kernel controls permissions, security-sensitive facts, budgets, external actions, verifier requirements, memory authority, and self-improvement writes.

The implementation must additionally support:

- The 104-model thinking-style registry.
- The 216-record routing configuration:
  - 212 measured historical records.
  - Four advisory counter-design records.
- IDF-weighted style routing.
- Mandatory protective thinking modules.
- Style completion contracts.
- The solo-contract micro-route.
- Independent verification and action attestation.
- Eight and only eight public terminal states.
- Persistent memory and competence updates.
- Governed self-evolution.
- Self-directed challenge discovery.
- A verdict-derived gap map.
- Human-approved learning plans.
- Sandboxed challenge trials.
- A tamper-evident learning ledger.
- Quick and monthly learning-history reviews.

## 1.2 Architectural thesis

Thinking Agent is not a single unrestricted model call and is not a generic reflection loop.

It is a composition of independently governed capabilities:

```text
Model generation
× problem framing
× causal diagnosis
× style routing
× planning and search
× independent verification
× safety authorization
× transactional execution
× persistent memory
× evaluation
× controlled learning
```

Generation, verification, authorization, execution, evaluation, memory writes, routing-knowledge updates, and ledger writes must remain distinct operations with different authority boundaries.

## 1.3 Public result contract

Every task MUST finish with exactly one of these statuses:

1. `SOLVED`
2. `APPROXIMATED`
3. `NEEDS_EVIDENCE`
4. `NEEDS_EXPERIMENT`
5. `INFEASIBLE`
6. `UNSAFE`
7. `ESCALATED`
8. `RESOURCE_LIMITED`

There is no public `ERROR` terminal status. Internal infrastructure failures must be recovered, escalated, or translated into one of the eight graceful outcomes.

Every outcome MUST contain a proof-carrying decision packet.

## 1.4 Auditability without exposing private chain-of-thought

The previous implementation plan required recording and returning raw “inner monologue.” That requirement is removed.

The implementation MUST NOT depend on, expose, or persist private model chain-of-thought. Instead, it must record structured, auditable reasoning artifacts:

- Claims and conclusions.
- Evidence references.
- Assumptions.
- Alternatives considered.
- Falsification conditions.
- Risk findings.
- Verification reports.
- Decisions and error bounds.
- Tool calls and observations.
- Gate results.
- Budget usage.
- Review lessons.
- Routing and style-selection records.

Provider-specific hidden reasoning fields MUST be discarded unless a provider exposes an explicitly safe summary field that is approved for persistence.

The following are not part of the initial production release:

- Autonomous model-weight training or fine-tuning.
- Autonomous deployment of solutions produced during SDL trials.
- General-internet SDL discovery from arbitrary webpages.
- Native multimodal reasoning.
- Embodied robotics.
- Unrestricted shell or Python execution.
- Autonomous replication.
- Automatic alteration of evaluation tests.

- Task-model writes to the World-Facts Store.
- Task-model writes to the routing KB or learning ledger.
- Docker or container-based deployment.
- Swarm-level orchestration inside this repository.

Bounded councils and parallel style passes are internal parts of one governed task. They are not a replacement for the external swarm orchestration layer.

# 3. Major Corrections to the Previous Implementation Plan

| Previous design | Required v8 replacement |
|---|---|
| Generic `Memory → Planner → Thinker → Critic → Finalizer` graph | Governed `META → WHAT → WHY → HOW → DO → REVIEW` graph with continuous verification |
| Raw append-only inner-monologue trace | Structured reasoning artifacts; no raw private chain-of-thought |
| One generic status field with `done/error` | Eight exact public terminal states |
| Model-controlled runtime configuration | Kernel-held World-Facts Store with immutable per-run snapshot |
| Critic score used as proof of correctness | Independent candidate verifier, outcome verifier, identity registry, reliability bars, and external judge |
| No separate authorization kernel | Explicit Safety Kernel, action-class attestation, authorization tokens, PENDING handling, and interrupts |
| Simple memory retrieval | Pre-hypothesis retrieval, hit pricing, real gap filling, provenance, contradiction handling, and authority tokens |
| No thinking-style implementation | 104 first-class style modules with 216 routing records |
| No routing confidence handling | IDF scoring, ambiguity routing, minimum-score curriculum-gap route, and mandatory gates |
| Generic parallel thinking | Bounded style passes, council roles, independent adjudication, and deterministic synthesis |
| Online learning declared a non-goal | Governed SDL planning, trials, ledger, review cycle, and absorb-and-learn |
| Automatic memory writes from reflection | Governed, provenance-aware commits and separate procedural authority |
| No learning history | Append-only, hash-chained Learning Ledger |
| No self-curriculum | Gap Map, discovery, Learning Plan, human gate, trials, and review |
| Outdated LangGraph 0.x assumptions | LangGraph 1.x `StateGraph`, `Command`, `Send`, `interrupt`, runtime context, and durable checkpointers |
| Docker-neutral but ambiguous deployment | Explicit native, no-Docker operating model |

## 4.1 Initial version targets

As of August 13, 2026, the initial lock-file targets should use LangGraph `1.2.9` and LangChain Core `1.5.0`, replacing the obsolete 0.x constraints in the previous plan. Pydantic Settings `2.14.2` is an appropriate initial configuration-management target. Exact transitive versions must be committed through a reproducible lock file. ([pypi.org](https://pypi.org/project/langgraph/?utm_source=openai))

| Category | Initial choice |
|---|---|
| Python | 3.12 as the baseline; 3.13 compatibility tested separately |
| Graph runtime | `langgraph==1.2.9` |
| Model abstractions | `langchain-core==1.5.0` |
| Validation | Pydantic 2.x |
| Settings | `pydantic-settings==2.14.2` |
| HTTP | `httpx` |
| Serialization | `orjson` where compatible; canonical JSON utility for hashing |
| Logging | `structlog` |
| Templates | Jinja2 |
| Configuration files | YAML plus Pydantic validation |
| Local checkpointer | LangGraph SQLite checkpointer |
| Production checkpointer | LangGraph asynchronous PostgreSQL checkpointer |
| Local knowledge index | SQLite FTS and pluggable local vector index |
| Production knowledge index | PostgreSQL/pgvector or an approved native vector store |
| Tests | pytest, pytest-asyncio, Hypothesis, respx |
| Static quality | Ruff, mypy or Pyright, Bandit, dependency audit |
| Telemetry | OpenTelemetry; LangSmith optional |

LangGraph supports typed graph state, per-key reducers, runtime context, dynamic control through `Command`, and map/reduce-style fan-out through `Send`. The implementation should use these primitives rather than emulating them in application code. ([docs.langchain.com](https://docs.langchain.com/oss/python/langgraph/graph-api?utm_source=openai))

Human approval nodes must use dynamic `interrupt()` calls with a durable checkpointer and `thread_id`. Approvals must be resumed with `Command(resume=...)`. Any operation before an interrupt must be idempotent because the node restarts when execution resumes. ([docs.langchain.com](https://docs.langchain.com/oss/python/langgraph/interrupts?utm_source=openai))

Development should use the asynchronous SQLite checkpointer, while production should use the asynchronous PostgreSQL checkpointer. Checkpoints provide task recovery; a separate Store or application repository is required for durable information shared across threads. ([docs.langchain.com](https://docs.langchain.com/oss/python/langgraph/persistence?utm_source=openai))

## 5.3 Process-boundary recommendation

The initial MVP may run in one Python process using strict interfaces and immutable objects.

The production release SHOULD separate:

1. Task graph process.
2. Kernel and policy process.
3. Judge/evaluation worker.
4. Tool-execution worker for external actions.
5. Scheduler and SDL review worker.

For local operation, these are native operating-system processes communicating over a Unix-domain socket, named pipe, or loopback interface. They do not require Docker.

# 6. LangGraph Decomposition

## 6.1 Graph inventory

| Graph | Responsibility |
|---|---|
| `TaskGraph` | Main governed problem-solving episode |
| `StylePassGraph` | Execute and validate one style module |
| `CouncilGraph` | Bounded parallel alternatives, debate, and verifier adjudication |
| `ExecutionGraph` | Plan authorization, approval, transactional execution, monitoring |
| `ReviewGraph` | AAR, reframe decision, lessons, competence proposal |
| `EvaluationEpisodeGraph` | Wrap a task in external judging and verdict-derived writes |
| `SDLCycleGraph` | Discovery, gap read, plan proposal, approval routing, review |
| `LearningPlanExecutionGraph` | Execute approved challenge items one at a time |
| `ImprovementEvaluationGraph` | Hidden tests, baseline comparison, canary, retain/rollback |

## 6.2 Why separate graphs are required

A single giant graph would:

- Mix task authority with judge authority.
- Make state reducers difficult to reason about.
- Increase checkpoint size.
- Make SDL writes appear to originate from the task model.
- Make human-approval interrupts harder to isolate.
- Complicate testing of terminal producers.

Subgraphs provide bounded state and clearer authority ownership.

## 6.3 Graph control primitives

- Use `Command(update=..., goto=...)` for nodes that update state and make a routing decision.
- Use conditional edges returning `Send` for bounded parallel style or council work.
- Use `interrupt()` for human decisions.
- Use graph reducers only for fields with safe associative merge behavior.
- Use single-writer nodes for selected decisions, status, authorization, and packet construction.
- Compile the parent graph with a durable checkpointer.
- Use per-invocation subgraph persistence unless a subgraph explicitly needs its own thread-level history.

## 6.4 Thread identity

Every run MUST have:

- `thread_id`: conversation or resumable execution identifier.
- `task_id`: immutable episode identifier.
- `run_id`: one graph invocation attempt.
- `checkpoint_id`: persistence-layer snapshot identifier.
- `decision_id`: selected decision identifier.
- `plan_id`: action-plan identifier.
- `world_facts_version`: immutable policy snapshot identifier.
- `prompt_bundle_version`: prompt set used.
- `model_registry_version`: model routing configuration used.

## 8.1 State-design rule

Use:

- `TypedDict` or dataclass schemas for LangGraph state.
- Pydantic models for domain objects and validation.
- Immutable dataclasses or Pydantic frozen models for kernel snapshots.
- Repository identifiers instead of database connections or model clients in checkpointed state.

# 9. World-Facts Store and Kernel Boundary

## 9.1 Configuration-channel separation

The implementation must distinguish four channels:

| Channel | Examples | Writable by task model |
|---|---|---|
| Task facts | User request, supplied constraints, context | No direct write after parsing; may be interpreted |
| Application configuration | Logging, provider endpoints, UI options | No |
| Kernel World Facts | Budgets, bars, identities, policy, allowlists | Never |
| Evaluation data | Verdicts, calibration, baseline results | Never |

## 9.2 Kernel-held facts

At minimum, the World-Facts Store owns:

- Stakes.
- Action taxonomy.
- Whether external action is required.
- Pending timeout.
- Iteration ceiling.
- Token ceiling.
- Cognitive-call ceiling.
- Agent-per-round ceiling.
- Deadline.
- EVOC base and decay.
- Novelty-plateau threshold.
- Gate re-entry budget.
- Reframe budget.
- Class reliability bars.
- Verifier identities.
- Second-verifier requirements.
- Verifier outage.
- Domain accuracy registry.
- Competence blend settings.
- Static PENDING allowlist.
- Stored-knowledge references.
- Fillable-gap policy.
- Trust margin.
- Consolidation threshold.
- Baseline-frozen status.
- Procedural-write authorization.
- Authority-token policy.
- SDL enablement.
- SDL pool minimum.
- Review cadence.
- Discovery budgets.
- Judge identity and calibration requirements.

## 9.3 Immutable run snapshot

At task initialization:

1. Kernel loads the active policy version.
2. Kernel validates its signature and schema.
3. Kernel produces an immutable `WorldFactsSnapshot`.
4. Runtime context receives a read-only facade.
5. Graph state receives only the snapshot reference and hash.
6. The snapshot remains fixed for that task, including after resume.

A policy change starts a new run or uses an explicit, audited migration. It must not silently alter a suspended task.

## 9.4 Production write boundary

Production SHOULD use separate database credentials:

- `agent_runtime`: read-only access to approved World Facts.
- `kernel_writer`: writes operator policy and approved evaluation updates.
- `judge_writer`: appends verdict-derived records.
- `ledger_reader`: read-only reporting access.
- `operator_admin`: migration and emergency administration.

For SQLite development:

- Place kernel data in a separate file.
- Open it read-only from the task process.
- Restrict filesystem write permissions to the kernel utility.
- Use a separate command-line administrative process for changes.

## 9.5 Read-path enforcement

The repository MUST include an AST-based `assert_read_path` test that:

- Identifies all names classified as security-sensitive knobs.
- Fails if task nodes read them from request, task state, model output, or generic runtime config.
- Requires access through the kernel runtime facade.
- Fails if a task node receives a mutable World-Facts object.
- Fails if a Pydantic model output schema contains a field that can override a kernel knob.

Behavioral tests must also prove that task-declared calibration, identities, pending timeouts, or allowlist hints are ignored.

## 10.2 Loop priority

At the beginning of every cognitive iteration:

1. Increment iteration.
2. Record loop audit event.
3. Check hard budgets.
4. Check call ceiling.
5. Check deadline.
6. Check loop monitor.
7. Check novelty plateau.
8. Respect pending and gate-wait exemptions.
9. Reserve enough budget for classification, packet construction, and checkpointing.
10. Route to the first incomplete stage.

Bookkeeping operations do not count as model calls, but their counts and latency must still be recorded.

## 10.3 E5 stabilization

If effort level is E5 and `stabilized` is false:

- Run exactly one containment-oriented stabilization pass.
- Record immediate hazards.
- Propose reversible containment actions.
- Do not perform root-cause diagnosis before stabilization.
- Mark `stabilized = true`.
- Continue to WHAT/WHY on the next iteration.

A stabilization pass does not authorize external execution. Any external containment action still passes through attestation and authorization.

# 11. Detailed Node Contracts

## 11.1 Bootstrap nodes

### `initialize_task`

**Type:** Deterministic  
**Inputs:** Public request and invocation context  
**Outputs:**

- Task and thread IDs.
- Empty state.
- Internal status.
- Runtime timestamps.
- Initial audit event.

**Rules:**

- Reject malformed requests.
- Do not accept security knobs in public input.
- Preserve unknown task metadata as untrusted metadata.
- Generate deterministic request hash.
- Never create a public terminal state here unless request validation itself makes the task infeasible or unsafe.

### `load_world_facts_snapshot`

**Type:** Kernel call  
**Inputs:** Environment, operator policy selector  
**Outputs:** `world_facts_ref` in state; immutable snapshot in runtime context

**Failure handling:**

- Missing or invalid kernel policy produces `ESCALATED`.
- Never fall back to task-provided defaults.
- Never start with an unsigned production snapshot.

### `resume_checkpoint`

**Type:** Deterministic persistence operation  
**Rules:**

- Verify checkpoint schema.
- Verify task/thread identity.
- Verify HMAC or integrity metadata.
- Rebind current runtime services.
- Restore idempotency records.
- Reject a checkpoint whose world-facts hash differs from the recorded snapshot unless an explicit migration exists.

## 11.2 META nodes

### `extract_preliminary_signature`

A preliminary signature is extracted from the request before WHAT. It is used only for:

- Effort estimation.
- Initial domain competence lookup.
- Initial budget sizing.

It does not finalize style routing.

### `meta_route`

**Inputs:**

- Request.
- Preliminary signature.
- Kernel competence view.
- Stakes.
- Budget policy.

**Outputs:**

- `RouteDecision`.
- Initial budget envelope.
- Method-composition flags.

**Model authority:**

The model may recommend effort, but the kernel clamps the recommendation to policy.

### `budget_guard`

**Type:** Deterministic  
**Responsibilities:**

- Verify iteration, token, call, agent, and deadline limits.
- Compute EVOC proxy from kernel facts.
- Evaluate novelty plateau.
- Exempt `pending_wait` and `gate_wait` from EVOC/plateau churn checks.
- Never exempt waits from hard timeouts or hard budgets.
- Map budget, EVOC, unproductive, and plateau stops to `RESOURCE_LIMITED`.

## 11.3 WHAT stage

### `frame_problem`

**Model output:** `ProblemFrame`

Required outputs:

1. Decision or problem statement.
2. Owner.
3. Success criteria.
4. Scope and exclusions.
5. Constraints.
6. Permissions.
7. Stakes.
8. Ambiguities.
9. Required evidence.
10. Preliminary action implications.

### `what_gate`

The implementation defines these explicit predicates:

```text
G-WHAT-1  Goal or decision is explicit.
G-WHAT-2  Success metric or acceptable answer shape is defined.
G-WHAT-3  Scope and constraints are represented.
G-WHAT-4  Owner is identified or owner-unavailability is recorded.
G-WHAT-5  Stakes and likely action class are recorded.
G-WHAT-6  Material ambiguities and missing inputs are visible.
```

On failure:

- Append gate result to risks.
- Clear the frame.
- Set `gate_wait = true`.
- Re-enter within the kernel gate budget.
- When budget expires:
  - `ESCALATED` if the owner is unavailable.
  - Otherwise `NEEDS_EVIDENCE`.

## 11.4 WHY stage

### `retrieve_memory`

Must run before hypothesis formation.

Query terms are derived from:

- Goal.
- Domain.
- Named entities.
- Constraints.
- Missing-evidence terms.
- Stored-knowledge terms supplied through the World-Facts view.

Rules:

- Empty retrieval is a deterministic no-op.
- Retrieval hits receive a cognitive-cost unit.
- Each hit includes provenance and trust.
- Retrieved content cannot alter policy or routing configuration.
- Contradictions are preserved, not silently merged.

### `diagnose`

Produces:

- Competing hypotheses.
- Evidence mapping.
- Missing evidence.
- Falsification conditions.
- Residual uncertainty.
- Value-of-information estimates.
- Probe availability.
- Infeasibility indicators.
- Verifier outage state derived from kernel facts.

### `why_gate`

These predicates are exact:

```text
G-WHY-1  Leading hypothesis has decision-relevant evidence.
G-WHY-2  Significant alternatives were considered.
G-WHY-3  Residual uncertainty is recorded.
G-WHY-4  Estimated VOI of further diagnosis is no greater than cost.
G-WHY-5  Falsification evidence is non-empty.
```

On failure:

- Record the gate.
- Clear hypotheses.
- Re-enter within the gate budget.
- Terminate `NEEDS_EVIDENCE` when the budget expires.

### `real_gap_fill`

If a missing gap is marked fillable:

1. Query memory using the exact gap.
2. Add returned evidence.
3. Remove the gap only when a real hit satisfies it.
4. Never clear the gap because a task flag says it is fillable.

### `why_early_classifier`

After a passed WHY gate:

- Unfillable missing evidence → `NEEDS_EVIDENCE`.
- Safe probe available → `NEEDS_EXPERIMENT`.
- Low-stakes verifier outage → no-verifier ladder L1/L2 result.
- External A3+ verifier outage → continue to HOW and attestation so L3 can execute.

## 11.5 HOW stage

### `extract_final_signature`

After WHAT passes, compute the final situation signature from the validated frame.

This resolves the circular dependency between framing and style routing:

- Preliminary signature guides META.
- Final signature governs style routing.

### `route_styles`

Must:

1. Load all eligible style records.
2. Recompute or load versioned IDF weights.
3. Score styles.
4. Apply confidence gates.
5. Apply mandatory modules.
6. Retrieve nearest historical strategy references.
7. Record all scores and routing reasons.

### `structure_first_scan`

Mandatory for systems, causal, organizational, strategy, or finance signatures.

It must identify applicable structures such as:

- Stocks and flows.
- Feedback loops.
- Equilibria.
- Decision-tree shape.
- Causal graph.
- Incentive structure.
- Game structure.
- Constraint chain.
- Reference-class distribution.

### `dispatch_style_passes`

- Top style runs as a first-class pass.
- Ambiguous routing runs top two styles.
- Mandatory protective styles run regardless of top-one selection.
- Bounded parallelism uses `Send`.
- Each branch receives a fixed budget permit.
- Branches cannot modify global state.
- Each branch returns a typed `StylePassResult`.

### `run_general_route`

The general governed route produces its own alternative set so it can be compared with style-pass conclusions.

### `divergence_resolution`

If style and general route agree:

- Record agreement and proceed.

If they disagree:

- Apply branch-completeness to both.
- Apply calibration to both.
- Record the disagreement.
- Select only after verification.

If a style pass fails its completion contract:

- General route governs.
- Style failure becomes a curriculum item.
- One bounded re-run may occur if budget permits.

### `council_dispatch`

Use only when META or routing confidence requires it.

Minimum roles:

- Proposal role.
- Counterproposal or falsification role.
- Independent verifier/adjudicator.

Requirements:

- Bounded to the kernel agent cap.
- Debate content references claims and evidence, not personality.
- Minority reports are retained.
- Final selection is not simple majority voting.
- Independent verification governs.

### `search_controller`

Used for tasks requiring combinatorial, planning, or hypothesis search.

Must provide:

- Search state.
- Expansion policy.
- Branch budget.
- Pruning policy.
- Stop condition.
- Novelty contribution.

### `constraint_screen`

Sets `infeasible = true` when:

- Hard constraints are inconsistent.
- No alternative satisfies mandatory constraints.
- Required resources are impossible within bounds.
- A plan’s own conditions establish infeasibility.

### `premortem`

Runs only when alternative content changed.

Must:

- Identify likely failure modes.
- Rank them.
- Connect them to alternatives.
- Avoid unbounded catastrophe enumeration.
- Add mitigations and residual risks.

### `verify_candidates`

Candidate reports may run in parallel, but each verifier identity is explicit.

Caching key:

```text
sha256(canonical_candidate_content + verifier_kind + verifier_policy_version)
```

### `select_decision`

Selection uses the reports belonging to each candidate.

The selected candidate’s reliability—not the highest reliability found anywhere in the set—must govern downstream checks.

If the selected decision includes an error bound:

- Set `approximation_available`.
- Classify as `APPROXIMATED`.
- Do not execute external actions unless approximation policy explicitly permits it.

### `how_gate`

```text
G-HOW-1  At least one viable alternative exists.
G-HOW-2  Required style completion contracts passed.
G-HOW-3  Hard constraints were screened.
G-HOW-4  Negative and failure branches were priced.
G-HOW-5  Selected candidate has a matching verifier report.
G-HOW-6  Residual risks and uncertainty are recorded.
G-HOW-7  External-action preconditions are explicit.
```

### `attest_action_class`

For external decisions:

- Independently estimate action class.
- Compare with declared/proposed class.
- Unknown defaults to A5.
- Misattestation → `UNSAFE`.
- `REPLICATE` action → `UNSAFE`.
- A3+ verifier outage at attestation → L3 `ESCALATED`.

### `selected_decision_verifier_check`

Before DO:

1. Resolve class reliability bar.
2. Read the report for the selected decision.
3. Block if selected reliability is below the bar.
4. Compute second-verifier requirement from kernel identity registry.
5. Block if the required identity count is absent.
6. Set `reliability_blocked`.
7. Route through the state-only classifier.

### `red_team`

Runs only on changed candidate content.

If a material flaw is found:

- Add the finding to risks.
- Reject the decision.
- Clear alternatives for regeneration.
- Return to HOW within the loop budget.

## 11.6 DO stage

### `build_plan_once`

The planner runs once per decision ID.

A plan rebuild is allowed only when:

- Decision ID changed.
- Plan was explicitly invalidated.
- A new authorization condition requires a revised plan.

### `authorize_plan`

Safety Kernel evaluates:

- Permissions.
- Action class.
- Risks.
- Reversibility.
- Tool scope.
- Required human approval.
- Static policy.
- Attestation.

Returns:

- Approved token.
- PENDING record.
- Unsafe denial.
- Escalation denial.

### `pending_allowed_subset`

When authorization is PENDING:

- Execute only tasks whose IDs appear in the static kernel table.
- Kernel taxonomy must classify them as A2.
- Ignore all task hints.
- Execute the subset at most once.
- Record zero executions when no eligible subset exists.

### `human_approval`

Uses LangGraph `interrupt()`.

Interrupt payload must include:

- Decision packet draft.
- Action class.
- Plan summary.
- Risks.
- Verification reliability.
- Requested permissions.
- Allowed subset already executed.
- Approval deadline.
- Available responses.

Valid responses:

- Approve.
- Approve with edits.
- Deny.
- Escalate.
- Timeout.

The pending-timeout scheduler must resume expired tasks with a timeout response. Waiting itself must not consume cognitive-loop iterations.

### `execute_transactionally`

For every plan task:

1. Validate authorization token.
2. Validate tool allowlist.
3. Validate Pydantic arguments.
4. Check action class.
5. Check idempotency key.
6. Execute with timeout.
7. Sanitize output.
8. Record receipt.
9. Add tagged untrusted observation.
10. Run compensation if required.

### `execution_monitor`

Checks:

- Unexpected output.
- Policy deviation.
- Partial failure.
- Cost overrun.
- Stop condition.
- Escalation condition.
- Compensation requirement.

### `plan_condition_router`

- Stop condition → terminal classifier, usually `INFEASIBLE` or another producer-owned state.
- Escalation condition → `ESCALATED`.
- Otherwise continue to verification.

## 11.7 VERIFY stage

### `verify_outcome`

Must independently check:

- Goal satisfaction.
- Required checks.
- External verifier presence.
- Reliability.
- Class bar.
- Second-verifier rule.
- Evidence sufficiency.
- Missing-evidence consistency.
- Executed-action results.

Outcome cache key:

```text
sha256(
  canonical(frame, hypotheses, alternatives, decision, observations)
  + verifier_policy_version

```

On cache hit:

- Reuse the verdict.
- Preserve reliability-blocked state.
- Record cache use.

`SOLVED` requires all mandatory checks to pass.

## 11.8 REVIEW stage

### `delta_review`

Runs only when:

- Candidate content changed.
- Observations changed.
- Verification is ambiguous.
- A decision exists.
- An action executed.
- A lesson source exists.

### `decide_reframe`

If review calls for reframing:

- Clear frame, hypotheses, and alternatives.
- Preserve evidence and audit history.
- Re-enter within the reframe budget.
- When budget expires, settle the best defensible frame and continue.

### `terminal_classifier`

Must be deterministic and state-only.

Classification order:

1. L2 no-verifier escalation.
2. L1 evidence degradation.
3. Ambiguous verification.
4. Reliability blocked.
5. Evidence gap.
6. Probe availability.
7. Infeasibility.

9. Approximation.

Runs only when a decision, action, or lesson source exists.

### `build_decision_packet`

Runs on every path.

### `audit_and_checkpoint`

# 13. Style Library and Router

## 13.1 Registry requirements

Startup MUST validate:

- Exactly 104 unique model IDs.
- IDs `m001` through `m104`.
- Required identity fields.
- Trigger schema.
- Strength and weakness fields.
- Model-family field.
- Completion-contract reference.
- Evidence status.
- No duplicate names without an explicit alias relationship.

## 13.2 Routing-record requirements

The router configuration must contain:

- 212 measured historical records.
- Four `DESIGN` counter records.
- Total: 216.
- Artifact references.
- Situation signatures.
- Historical outcome.
- Strategy lesson.
- Model association.

Design records:

- Must not contribute to `pos_win_rate`.
- Must not contribute to `neg_failure_rate`.
- Must not create Gap Map entries.
- Must not be represented as judge verdicts.
- May be used in explicitly enabled canary evaluation.

## 13.3 IDF scoring

For each trigger term:

```text
idf(term) = log((1 + model_count) / (1 + models_containing_term)) + 1
```

For each model:

```text
weighted_match =
  Σ idf(matched domain terms)
+ Σ idf(matched goal terms)
+ Σ idf(matched context terms)

route_score =
    weighted_match × pos_win_rate
  - 0.5 × neg_failure_rate
```

All score components must be recorded.

The scoring policy is versioned. Any scoring change requires router regression.

## 13.4 Routing-confidence gates

```text
G1  If top1 - top2 <= 0.5:
    run top two passes and synthesize.

G2  If top1 <= 1.0:
    use the general route plus mandatory protective gates;
    record a curriculum gap.

G3  Record signature, scores, records, and gate in the packet.

G4  Recompute IDF after every approved curriculum KB update.
```

## 13.5 Mandatory modules

- `adversarial` → m019 adversary pass.
- `one_shot` or `high_stakes` → m007 ruin screen.
- `unmeasured` → m006 provenance audit.
- `guarantee` → prepend m003 inversion.
- `maximize` → require risk pass and falsifiable checkpoint.

## 13.6 Completion contracts

Explicit typed contracts are required for at least:

- m003 Inversion.
- m006 Provenance/Bayesian audit.
- m007 Ruin screen.
- m011 Systems scan.
- m019 Adversary pass.
- m022 Branch enumeration.
- m033 Experiment design.
- m097 Reference-class forecast.
- m101 Bayesian precision counter.
- m102 Likelihood-audit counter.
- m103 Sequential constraint counter.
- m104 Dynamic Five-Forces counter.

Every other style must have:

- Required outputs derived from its strengths.
- A weakness/trap checklist.
- A protective-gate association where applicable.
- A maximum pass budget.
- A contract-validation method.

A pass that does not meet its contract is recorded as incomplete.

## 13.7 Solo-contract micro-route

Activate only when:

- Top-one style is high confidence.
- Score gap exceeds 0.5.
- Signature is complete.
- Task is closed-scope and fully specified.
- One style’s discipline is the complete answer.
- Required protective checks can be inlined.

Behavior:

- Run one first-class style pass.
- Inline contract checks.
- Do not create separate machinery prose.
- Preserve kernel gates and verification.
- Do not bypass safety or evidence requirements.

## 13.8 First-class-home-turf rule

A style matching the core structure of the task must run as its own pass even if initially ranked second or third.

This promotion must be deterministic and audited.

Examples:

- Industry-structure decision → Five Forces.
- Serial-flow constraint problem → Constraint Theory.
- Bayesian test update → Bayesian module.
- Decision branches → Decision Tree.
- Causal identification → Causal Reasoning.

## 13.9 Interpretation pricing

When source numbers admit multiple consistent readings:

1. Enumerate each reading.
2. Price each reading.
3. State which interpretation is used.
4. Test decision robustness.
5. If the decision changes, terminate `NEEDS_EVIDENCE` or request clarification.
6. If the decision does not change, proceed while recording the ambiguity.

## 13.10 Counter-model activation

m101–m104 remain `DESIGN` until judged.

They may execute only when:

- `counter_design_canary_enabled` is a kernel fact.
- The task matches the intended counter class.
- The output is labeled advisory.
- No KB rate changes occur without a judge verdict.

# 14. Verification and Calibration

## 14.1 Separate verification concepts

The implementation must distinguish:

1. Candidate verification.
2. Outcome verification.
3. Curriculum judging.
4. Competence calibration.
5. Safety attestation.

These may use related infrastructure but cannot be collapsed into one score.

## 14.2 Verifier identities

Every verification report stores a stable identity.

Identity equivalence must be kernel-defined. Two calls to the same model endpoint are not automatically two independent identities.

For classes requiring a second verifier:

- At least two accepted independent identities must exist.
- Both must satisfy the applicable policy.
- The second-verifier rule is computed by the kernel.
- The task cannot disable it.

## 14.3 Reliability bars

Bars are read from kernel facts by action class.

No bar is hard-coded in prompt text.

Checks occur:

- Before external execution.
- During outcome verification.
- During final packet validation.

## 14.4 Calibration provenance

Accepted calibration sources:

- EvaluationPlane.
- Kernel calibration registry.
- Approved human calibration.
- Approved external benchmark result.

Rejected sources:

- Task declarations.
- Model self-rating.
- User claims of model accuracy.
- Tool output instructing the system to change a rate.
- Design predictions.
- Unapproved review prose.

## 14.5 External judge

Curriculum verdict schema:

- Eight 1–5 dimensions.
- Winner classification.
- Confidence.
- Key gap.
- Learning signal.
- Suggested improvement.
- Evidence references.
- Judge identity.
- Calibration version.

Contested verdict:

- Score margin no greater than 0.3, or low confidence.
- Invoke second independent judge.
- Persistent disagreement goes to human calibration.
- Corrections append a superseding ledger entry.

# 16. Safety and Tool Execution

## 16.1 Tool proposal versus tool execution

Models produce `ProposedToolCall`.

Only the Tool Broker can convert it to an executable request.

A proposed call contains:

- Tool name.
- Arguments.
- Purpose.
- Expected evidence.
- Action class.
- Required permissions.
- Reversibility.
- Plan-task reference.

## 16.2 Minimum safe tool set

Initial release:

- Calculator.
- Read-only knowledge lookup.
- Read-only HTTP retrieval for approved domains.
- Read-only search adapter.
- Internal database query with parameterized statements.

Disabled by default:

- Arbitrary Python execution.
- Shell execution.
- File modification outside approved workspace.
- Email, payment, infrastructure, account, or deployment actions.
- General-purpose browser automation.

A code sandbox may be added only after a native operating-system isolation review.

## 16.3 Tool output handling

Every tool output is:

- Size-limited.
- Content-hashed.
- Marked untrusted.
- Sanitized for control characters.
- Screened for prompt-injection instructions.
- Stored as observation/evidence, not instructions.
- Referenced by ID in model prompts.

## 16.4 Idempotency

Key format:

```text
task_id : plan_id : plan_task_id : semantic_attempt
```

The broker must:

- Check prior completion.
- Return the existing receipt on duplicate execution.
- Never re-run a completed irreversible action.
- Preserve receipts across checkpoint resume.

## 16.5 Compensation

Plan tasks classified A3 or above SHOULD declare:

- Compensation action.
- Compensation preconditions.
- Compensation deadline.
- Whether compensation is complete, partial, or impossible.

## 16.6 Replication denial

Any action classified as replication, self-copying, or unauthorized autonomous propagation is denied by attestation and returns `UNSAFE`.

- Full ledger analysis.

- Multi-cycle trends.

- Rejected.
- Escalated.
- Re-budgeted.

- Rejected with reason.

- Planned.
- Attempted.
- Closed.

# 23. Error Handling and Recovery

## 23.1 Error taxonomy

| Type | Handling |
|---|---|
| Transient provider error | Retry with bounded backoff |
| Provider rate limit | Retry or approved fallback |
| Schema validation failure | One repair attempt, then fallback/terminate |
| Tool timeout | Record failure; retry if idempotent |
| Tool validation failure | No retry; return to planner |
| User-correctable input gap | `NEEDS_EVIDENCE` or interrupt |
| Policy denial | `UNSAFE` or `ESCALATED` |
| Verifier outage | No-verifier ladder |
| Budget exhaustion | `RESOURCE_LIMITED` |
| Persistence failure | Stop side effects; escalate or resource-limit |
| Integrity failure | `ESCALATED`; do not resume |
| Judge failure | Trial remains unjudged; no learning writes |

## 23.2 Retry rules

- Retries must be configured per node.
- Do not retry validation or policy errors.
- External action retries require idempotency confirmation.
- Judge retry cannot create duplicate ledger entries.
- Discovery retries cannot duplicate candidate records.

LangGraph supports node retry policies for transient failures; project-specific retry filters should distinguish transient transport errors from invalid inputs and policy failures. ([docs.langchain.com](https://docs.langchain.com/oss/python/langgraph/thinking-in-langgraph))

## 23.3 Interrupt safety

Because an interrupted node restarts:

- Do not perform non-idempotent side effects before `interrupt()`.
- Proposal persistence before an interrupt must use a stable idempotency key.
- Approval application occurs after resume.
- Duplicate resume payloads must be harmless.
- Pending-subset execution must be separately idempotent.

# 31. Final Implementation Principle

The implementation must preserve the central architectural separation:

```text
The model may propose.
The verifier may check.
The kernel may authorize.
The executor may act.
The judge may score.
The ledger may record.
The improvement pipeline may change the system.
No single component may perform all of these roles.
```

The first milestone is not “make the model think longer.” It is to build the governed state, trust boundaries, terminal-state contract, and proof-carrying packet. Style routing, execution, memory, self-evolution, and self-directed learning are then added behind those boundaries.

The system is production-ready only when its control-flow, security, verification, persistence, and learning-write restrictions are demonstrated through execution—not merely described in prompts or documentation.
